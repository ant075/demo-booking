## Как использовались AI-инструменты?

claude CLI для:
 - поиска проблем,
 - выработки решений,
 - написания тестов,
 - подготовки тестовых данных,
 - проведения предварительного ревью кода.

codex CLI для проведения предварительного ревью кода.

AI-инструменты я в этот раз использовал без размаха, экономя токены, т.к. сейчас располагаю учётной записью с ограниченным тарифным планом.

Код я писал сам, сделав исключение для тестов, которые частично написаны claude, и SQL-сидера тестовых данных (более 1 млн. записей в bookings для тестирования производительности запросов), который claude создал целиком.

## Примеры промптов

### Пример 1: поиск проблем

> смотри app/Http/Controllers/BookingController.php. Пользователи жалуются на ошибки. Найди их и перечисли, указав степень важности по шкале critical / major / minor.

Результатом стали 8 пунктов REVIEW.md. Потом я дополнил их собственными пунктами.

### Пример 2: написание тестов

> просмотри последние 3 коммита и добавь feature-тесты на внесённые этими коммитами изменения

Результатом стали 8 тестов в классе BookingStoreTest.

Один написанный claude тест test_working_hours_are_checked_in_utc_regardless_of_submitted_offset оказался лишним, я его убрал. Его появление было следствием того, что я на тот момент ещё не приводил время к TZ офиса для его проверки рабочего времени. А в UTC проверять было не надо.

После добавления проверок времени бронирования по времени офиса:

> теперь добавь feature-тесты для текущих изменений файла Http/Controllers/BookingController.php по сравнению с последним коммитом.
 
Результат: ещё 5 тестов.

Я проверил исходный код всех тестов, созданных claude. Остальные тесты написал руками.

### Пример 3: подготовка тестовых данных

Здесь не обошлось одним промптом, данные готовились итеративно, по мере уточнения мной требований:

> создай тестовый seeder (просто sql-файл), заполняющий таблицу bookings тестовыми данными за последние 3 года. Вот структура таблицы:

> _... SQL-код создания таблицы ..._

> seeder положи в каталог _wrk

Полученный сидер сгенерировал бы 2383 записи. А я хотел проверить на 1 млн. записей. Поэтому:

> нужно примерно в 500 раз больше записей.
 
Создано более 1 млн. записей. Но они перекрываются в пределах 1 комнаты. Поэтому уточняем дальше:

> измени _wrk/bookings_seed.sql так, чтоб не было записей с перекрывающимися интервалами startrs_at - ends_at. Совпадение предыдущего ends_at с последущим stars_at допустимо.

... очередная итерация. С бронями, в том числе, нулевой длины. Исправляем:

> брони продолжительностью 0 недопустимы. пусть брони будут длиной 15 минут - 1 час. И увеличь количество лет, за которые создаются записи. Цель — не менее 1000000 записей.

В итоге получен скрипт, который создал более 1 млн. не перекрывающихся записей за 120 лет :-).
Этот скрипт для локального тестирования, в репозиторий не добавлен.

## Пример, когда я не послушал ИИ

Изначально, без консультаций с AI, было понятно, что в таблице должен быть индекс помимо первичного. Он должен покрывать потребности запросов на поиск существующих броней, перекрывающихся с запрошенной бронью при её создании. Я предполагал создать обычный составной btree-индекс по полям room_id, starts_at, ends_at. Но решил дать свободу поиска claude. Поэтому задал ему вопрос, оттолкнувшись от очевидно плохих результатов explain analyze:

<pre>
я применил сидер. вот результаты
explain analyze
select id
from bookings
where room_id = 1
and starts_at <= '2026-11-02T08:00:00+00:00'
and ends_at >= '2026-11-02T07:00:00+00:00'
Gather  (cost=1000.00..25446.48 rows=1542 width=8) (actual time=47.787..54.581 rows=1 loops=1)
Workers Planned: 2
Workers Launched: 2
  ->  Parallel Seq Scan on bookings  (cost=0.00..24292.28 rows=642 width=8) (actual time=38.659..38.660 rows=0 loops=3)
Filter: ((starts_at <= '2026-11-02 08:00:00'::timestamp without time zone) AND (ends_at >= '2026-11-02 07:00:00'::timestamp without time zone) AND (room_id = 1))
Rows Removed by Filter: 391464
Planning Time: 0.069 ms
Execution Time: 54.601 ms

что улучшить?
</pre>

claude предложил 2 варианта: тот же btree-индекс, который собирался применить я, и альтернативный вариант: GiST/exclusion constraint.
Суть этого предложения была в том, чтобы добавить в БД расширение btree_gist, а затем добавить в таблицу bookings ограничение
```SQL
ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
EXCLUDE USING gist (
room_id WITH =,
tsrange(starts_at, ends_at) WITH &&
)
```
Помимо ускорения поиска, это решало и проблему с перекрытием броней на уровне БД, а не приложения: запрещало создание перекрывающихся броней для одной room_id как ограничение БД.
Тогда не требовалось бы перед созданием новой брони искать существующие брони, потенциально перекрывающиеся с ней. Мы бы сразу пытались создать бронь, при наличии перекрывающихся броней PostgreSQL бросал бы исключение, требовалось бы его корректно обработать, вернув клиенту ошибку 409 "Комната занята". Это устраняло race conditions, описанную как бонус!

Тестовое применение этого решения на 1 млн. строк действительно показало улучшение производительности по сравнению с btree-индексом. При этом новый GiST-индекс я создавал при уже наполненной таблице.

Я изучил вопрос и нашёл в Интернете жалобы на постепенную деградацию GiST-индекса при многократном добавлении данных. Он хорош сразу после переиндексации, но потом производительность деградирует.
Решил это проверить.

Все записи bookings я удалил через truncate. Удалил индексы и ограничения. Добавил к пустой таблице GiST-индекс через указанное выше ограничение. А _потом_ снова создал более 1 млн. записей и выполнил указанный выше eхplain analyze. Продолжительность поискового запроса стала **вдвое больше**, чем без всякого индекса! Гипотеза деградации подтвердилась.

Вообще говоря, защита модели данных средствами самой СУБД лучше, чем только средствами приложения. Однако, реализация варианта с GiST-ограничением требует, как минимум, регулярной переиндексацию для предотвращения деградации индекса. В целом, это решение видится содержащим некоторую неопределённость в поведении. В лучшем случае, оно требует дополнительного изучения и тестирования на массе данных в течение заметного времени.

Но я выбрал другой вариант:
1. Добавить обычный btree-индекс для ускорения предварительного поиска перед созданием брони.
2. Проблему race conditions решать иначе, через безопасную (автоматически снимающуюся) блокировку pg_advisory_xact_lock. Это решение подсказал claude, но я его проверил вручную, см. ниже.

Выбранный мной вариант имеет следующие преимущества:
1. Никакой неопределённости в поведении.
2. Не нужны никакие дополнительные меры вроде периодической переиндексации, решение самодостаточно.

## Что я проверил вручную и что сознательно не доверил ИИ

Я вручную проверял код созданных ИИ тестов. Кроме того, тестировал те же кейсы внешними запросами через curl.

Ключевые решения принимал после проверки вариантов решения экспериментом, см. п. "Пример, когда я не послушал claude"

Когда по подсказке ИИ устранил проблему race conditions через pg_advisory_xact_lock, то проверил ситуацию гонки вживую дважды: без исправлений и с исправлениями. В итоге надёжно воспроизвёл ситуацию гонки и создание конфликтующих записей без исправления. А потом убедился, что с исправлением (с блокировкой) один из запросов надёжно создаётся 1 запись, а второй запрос возвращает 409 "Комната занята".
Как я воспроизвёл ситуацию гонки, описано в файле _wrk/race-conditions-test.txt.
